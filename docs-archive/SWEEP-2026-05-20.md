## Phase 3: Deep reads of high-risk files

### F5 — SIZE — `element-detail.ts` (1444 lines) is the strongest split candidate

- **Severity**: MED (works fine, but maintenance pain growing)
- **Where**: `src/middle/element-detail.ts`
- **What**: One file holds ~5 distinct concerns. The split would mirror the session 212 `map-tab.ts` split that's worked well.
- **Suggested split**:
  - `element-detail-header.ts` (~450 lines): `renderHeader`, `buildSyncDot`, `renderWritingTierActions`, `renderMapPinClusters`, `renderMapPinnedElementStrip`, `buildPinnedElementIcon`, `navigateToPinnedElement`, `buildSelfOpenMapAffordance`, `buildMapAffordance`, `buildPinAffordance`, `buildClusterDivider`, `deletePinFromHeader`, `startInlineNameEdit`
  - `element-detail-fields.ts` (~350 lines): `renderSection`, `renderField`, `renderSingleLink`, `renderMultiLink`, `buildLinkChip`, `persistFieldPatch`, `autoUpdateMapDims`, `suggestionsForField`, `pickIconFor`
  - `element-detail-refs.ts` (~80 lines): `renderReferencedBy`, `buildRefChip`, `findIncomingReferences`, `refersTo`
  - `element-detail.ts` (~250 lines): public mount + render dispatcher + scroll memory + module-level state + footer + `onDelete` + `humanizeFieldName` + `formatValue` + `forceRerender`
- **Why it's worth doing**: The writing-workspace redesign you mentioned will likely touch this file heavily (custom layout for narratives). Smaller files = easier to redesign one concern without touching the others.

#### F6 — DUP — `buildNarrativeIndex` exists in two places with subtle differences

- **Severity**: MED
- **Where**: `src/sidebar/writing-sidebar.ts:43` (full version with `roots`, sorting, depth assignment) AND `src/middle/writing.ts:52` (stripped version, only `byId`, no sort).
- **What**: Same conceptual function, two implementations. `NarrativeNode` and `NarrativeIndex` types are also duplicated. Future edits could diverge silently.
- **Suggestion**: Move canonical `buildNarrativeIndex` (the full sorted version), `NarrativeNode`, `NarrativeIndex` to `src/middle/writing-helpers.ts`. Both callers import. Same destination as `writingHashForNarrative` and `isWritingNarrative`.

#### F7 — DUP — `findAncestry` overlaps `writingHashForNarrative`

- **Severity**: LOW
- **Where**: `src/sidebar/writing-sidebar.ts:93` (`findAncestry` returns `{bookId, chapterId, sceneId}` for path construction); `src/middle/writing-helpers.ts:95` (`writingHashForNarrative` walks parent chain to build URL).
- **What**: Both walk `parent_narrative` chain to recover ancestor ids. Different return shapes; same underlying walk. Could share an internal `walkParentChain(elements, id)` helper.
- **Suggestion**: Extract `parentChain(byId, id): Element[]` in writing-helpers; both consumers reshape it.

#### F8 — UNDER-ABSTRACT — `store.update + list + patch + requestPush` repeats ~25 times

- **Severity**: MED
- **Where**: 22+ files, mostly `element-detail.ts` (4x), `writing-sidebar.ts`, `writing.ts`, all map-tab modules, all zone modules, several modals. See grep below for the inventory.
- **What**: The pattern `const elements = await store.listElements(); patchSlice('data', { elements }); requestPushIfLinked();` (often preceded by `await store.updateElement(...)` or `await store.deleteElement(...)`) appears verbatim at ~25 call sites. Some variants also toast.
- **Suggestion**: Extract `refreshElementsAfterWrite(store)` helper (3 lines → 1 line at each call site). Could live in `src/core/active-store.ts` or a new `src/store/commit.ts`. Risk: callers that want to skip refresh in specific cases (rare) need an opt-out. Worth doing — 22 → 1 location for changes to the refresh-after-write semantics (e.g. future flush-immediately option).

#### F9 — SIZE — `sync-engine.ts` (1398 lines) is coherent but `pushPhase` is dense

- **Severity**: LOW (works correctly, well-commented)
- **Where**: `src/sync/sync-engine.ts:691-1050` — `pushPhase` is ~360 lines.
- **What**: The try/catch in `pushPhase` discriminates 4 error categories: auth (401/403), 404 on UPDATE (server-delete routing), FK constraint on CREATE (peer-deleted routing), and generic per-element failures. The if/else cascade is correct but dense.
- **Suggestion**: Extract `categorizePushError(err, elem, isCreate, folder): Promise<{kind, ...}>` returning a discriminated union. pushPhase iteration becomes a switch on the kind. Each handler is ~10 lines, easier to test independently. Class-level structure stays — the engine remains a single class.

#### F10 — SIZE — `settings-panel.ts` (885 lines) per-tab split candidate

- **Severity**: LOW
- **Where**: `src/middle/settings-panel.ts`
- **What**: Six tabs (identity / atlas / sync / world / maps / writing / about) each rendered by a `wireIdentityTab` / `wireSyncTab` / etc. function. Could split into one file per tab, with `settings-panel.ts` as the orchestrator/router.
- **Suggestion**: `settings/identity-tab.ts`, `settings/sync-tab.ts`, etc. Reduces blast radius when adding a tab feature.

#### F11 — BRITTLE — `getElement` cold-path scans every type's index

- **Severity**: LOW (already in soft-edges)
- **Where**: `src/store/folder-store-fs.ts:318-341`
- **What**: On cache miss, `getElement` iterates `ALL_ELEMENT_TYPES` (22) to find the type containing the id. Most calls hit warm cache; this branch is rare but does 22 directory probes worst-case.
- **Suggestion**: Already in 3.6+ soft-edges. Caching id→type would close it.

#### F12 — BRITTLE — `setTimeout(0)` for post-layout focus

- **Severity**: LOW
- **Where**: `src/ui/field-edit-popover.ts:135`
- **What**: See F4 in convention audit. Idiomatic equivalent is `queueMicrotask` (already used elsewhere in the same file).
- **Suggestion**: Replace.

#### F13 — Notes from `mountWriting` post-sidebar-takeover

- **Severity**: LOW
- **Where**: `src/middle/writing.ts`
- **What**: After session 224's sidebar takeover, `mountWriting`'s `mountEditor` does very little — empty state + selection mirroring + re-mounting element-detail. The file has 304 lines but most are leftover empty-state HTML and the duplicated `buildNarrativeIndex`. Consolidation candidate.
- **Suggestion**: With F6 consolidation, `writing.ts` shrinks to ~150 lines focused purely on mode dispatch (setup / editor / empty) + the contextual create flow.

#### F14 — Patterns I noticed (thematic)

- **Module-level mutable state** is used in several places (element-detail's `scrollMemory`, `collapsedSections`, `pendingAutoEditNameForId`; map-tab caching; writing-sidebar's `lastExpandedForActiveId`). The pattern works but means tests have to reset state via exported helpers. Currently `resetElementDetailScrollMemory` exists for one of these — consider a uniform `resetUiCaches(worldId)` hook called on world switch.
- **Type assertions `(el as Element & { foo?: T }).foo`** appear in many spots — narrative parent_narrative, marker zone_id, pin element_id. Could be addressed with a proper discriminated-union `Element` type on top of `ElementType`, but the SDK schema is type-erased dynamic so this might require generating typed shapes. Track as a longer-horizon question, not a current bug.
- **Many places use `as any`** for SDK-schema-driven property access. This is fundamentally unavoidable without a code-gen pipeline. Documented as fine.

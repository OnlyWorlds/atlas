# S334 — the union read, and the fixture that watches it

**2026-07-28 21:5x** · Temper · Captain's mandate: *"get on top of Kael's messages; might require some atlas digging... before you get all tangled up"* → then *"roll on, take as long and deep as you like"*

**One line**: atlas could not open a world written by anyone else, silently. It can now, and a committed fixture will say so out loud the day that stops being true.

---

## 1. What was wrong

`elements/<type>/` is the Folder Format for all 22 types (spec v0.3, my own ruling, credited in §4). Atlas was the only implementation that ever split maps, pins, zones and markers into `spatial/<type>/` — the Leaflet subsystem's convenience leaking into the serialization — and it read **only** there.

So a spec-conforming capture opened in atlas showing every content element, a clean UI, and no maps, pins, zones or markers, **with no warning anywhere**. Kael has two verified captures (36 and 1,087 elements) and a live Blood Meridian world carrying 1 map + 1 zone that shipped atlas could not show. A world that looks complete while missing an entire subsystem is the exact failure the format exists to prevent.

## 2. What shipped

**The read**: `buildIndexFor` scans both layouts for spatial types and merges. Split into `scanLayoutFor(type, layout)` (one directory: read, group by body id, dedupe crash twins) + a merge in the caller.

**The write**: every `fileIndex` entry records the `layout` its file was found in, and every write / rename / unlink / sync-stamp goes back to that directory. New worlds write `elements/` for all 22 and **never create `spatial/`**. A folder already holding spatial files keeps receiving them there — detected once at open by FILE presence, because an empty `spatial/map/` is litter from the old `ensureLayout`, not a layout.

**The deletion I did not do**: same id in both directories serves the newest `local_updated_at` (ties to `elements/`), warns naming both paths, and **touches neither file**. Same-directory duplicates are a rename crash and still dedupe. Resolving a stranger's folder by deleting half of it is not atlas's call.

**The API change worth noting**: `elementDirSegments(type)` is deleted, replaced by `elementDirSegmentsIn(layout, type)`. The old signature inferred `spatial/` from the TYPE, which made the layout an invisible property of the type rather than of the FOLDER — the defect had no call site to blame because nobody ever decided it. No caller can omit the layout now.

**The tidy** runs per (type, layout): two directories are two occupancy spaces. It is scheduled AFTER the index is populated — my first cut scheduled it inside the scan, where it would have read an empty occupancy view and quietly converged nothing. A file shadowed by the merge is absent from the index and therefore never renamed.

## 5. Skeld's two flags, answered

Method stated honestly: **source read of every site + its guard**, not a live probe.

- **Mapless pins degrade correctly.** `element-detail-header` narrows `map_id` to `string | undefined` and renders no affordance when absent; every map filter compares `map_id === mapId`, so an absent one never matches. The fixture now proves it loads and the live open proves the canvas mounts.
- **`<img src="">` does not reproduce in atlas.** All 18 `img.src` / `src=` sites are guarded by truthiness or an `^https?://` test; `buildPagePayload` only emits `image_url` when non-empty and requires an http(s) URL for map blocks; the four off-DOM `new Image()` helpers take their url from `resolveMapImageSource`, which returns `{kind:'url'}` only for a non-empty string.
- **One honest divergence**: absent `marker.order` is tolerated everywhere (`?? 0`), but atlas does **not** fall back to `created_at` as his consumer rule states, so a fully order-less zone draws in file-scan order. Small, real, not worth a bout today.

## 5b. ★ THE CLOSING ACT: Kael's real capture, and the field that fell through

Skeld's letter named the biggest open gap in the format's evidence: Kael's writer had never been opened in a live reader. I closed it with the real artifact rather than my fixture — **a fixture carries my assumptions and none of the producer's**, which is precisely the law this case exists to illustrate.

Ran his built `dist/cli.js` against demo world 0 (read key, output to my scratchpad, nothing in Assembly touched), seeded the capture into OPFS byte for byte, opened it through the real open-folder path.

**36 of 36 elements**, matching his `snapshot_counts` exactly, including the 1 map / 1 pin / 1 zone / 6 markers that shipped atlas would have shown NONE of. Charts renders his dated events with era bands and a live calendar lens, so `atlas_calendar` — a nested object on a Construct — round-tripped through his writer intact.

**⚡ AND IT FOUND A SECOND UNRULED RENAME.** His `world.json` carries `"time_range_current": 0` (the wire name, verbatim, exactly as the spec instructs). Atlas's DISK name is `time_current` (`sync/world-meta-sync.ts:44`, "the one disk↔wire rename"). So:

```
time_basic_unit  ✓   time_range_min/max  ✓   time_current  ABSENT   time_range_current  present, unread
```

A captured world loses its **now**: no gold now-line in charts, and a "set now time" button offering to set a value the folder already holds. Measured off the live meta object, screenshot `ui-snapshots/2026-07-28-union-read/04-kael-capture-charts.png`.

Neither implementation is wrong under the current spec. This is the **same class as §5's bare-link-fields ruling that I made and never built**: atlas holds disk↔wire renames the format never adjudicated, and each one is a silent data loss the day a second implementation appears. That is two, both mine, and this one only surfaced because someone finally wrote the other dialect to disk.

**Not fixed tonight, deliberately.** It is a disk-contract question spanning a spec, a writer and a reader; ruling it from inside one implementation at midnight is the exact move that produced the `spatial/` split. Recommendation sent to Skeld: rule the WIRE name canonical on disk (consistent with §5's "bare schema names, uniformly"), atlas reads both forever and converges its own writes. Banked with this repro.

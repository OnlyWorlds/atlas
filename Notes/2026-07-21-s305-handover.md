## The schema findings that reshaped the design

Captain asked to "drag in the old Steinway and/or Rachmaninov to show RANGE".
Neither can, and this is worth telling him:
- **Objects are not dateable at all** — `object` has no entry in

## THE FRAMING FIX IS REVERTED. Do not re-apply it as written.

Two BLOCKERs, both demonstrated with real numbers rather than source-reading:

1. **`coverageIntervals` read `node.endDate` raw and never `effectiveEndDate`.**
   An OPEN-ENDED node (a `title` with a grant and no revoke) has `endDate: null`,
   so its coverage interval was a POINT even though it RENDERS as a bar to `now`.
   It was therefore trimmed as an outlier while visually spanning the very gap
   the algorithm called empty. Measured: title(grant 0, open) + 6 events at
   1900-1950, now 2000 → default window `[1899, 1951]`, i.e. 95% of the bar off
   screen. **My own docstring claimed this case was handled.** The test I wrote
   for it used a RECORDED end, so it exercised a different path entirely.
2. **`extendRangeForOpenEnds` iterates ALL nodes, including trimmed ones**, so a
   discarded open-ended node dragged `max` back out and produced a window WIDER
   than the plain fit. Measured: 8 events at 0-70 + title(grant 4000, open),
   now 5000 → plain fit span 4160, post-trim-post-extend span **5101**. The
   smear fix made the smear worse for that shape.

Also found: the FOCUSED element could be framed off-screen (nothing pulls `min`
back to include it); `zoomFactorOf` derives LOD rungs from `baseRange`, so the
framed view shipped with SMALLER glyphs and fewer labels than before; `total` was
stale across trimming passes (the shipped chain test passed for arithmetically
wrong reasons); and a "no-op" test passed vacuously via an earlier early-return.

**The spec for doing it properly**, when it gets a fresh session:
- coverage intervals must use `effectiveEndDate(start, end, openEnded, now)`, so
  `calculateDefaultWindow` needs `now` passed in;
- `extendRangeForOpenEnds` must run over the KEPT nodes, not all of them (or the
  trim must run after it);
- the focus node must be force-included in the window;
- decide deliberately what `zoomFactorOf` should divide by — the framed window or
  the data extent — because LOD depends on it;
- recompute `total` per pass;
- test at the 5/6 node boundary, at the exact ratio thresholds, and with an
  open-ended node present.
Upheld and worth not re-verifying: no inverted/empty range is reachable, ties
keep everything, NaN/Infinity are guarded, `endDate < startDate` normalizes, the
user can never get stuck (navBounds always uses the untouched full-universe
range), and the overview strip band stays correctly placed.
